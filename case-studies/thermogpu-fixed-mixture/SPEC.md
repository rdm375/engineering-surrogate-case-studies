# Case Study 2 — Fixed-Composition Multicomponent EOS

## Question

How does the economic value of a hardware-executable surrogate change as
the computational complexity of the underlying physical model increases
while the dimensionality of the surrogate input remains fixed?

More specifically:

> When does approximation become cheaper than direct physics for
> fixed-composition Peng–Robinson mixture EOS evaluation?

## Scope

The study compares direct Peng–Robinson EOS evaluation with TDAR-derived
CPWA surrogates for compressibility factor Z over a fixed two-dimensional
input domain:

- temperature T: 250–350 K
- pressure P: 1–10 MPa
- composition fixed within each mixture
- binary interaction coefficients zero

The surrogate input dimension therefore remains two, `(T, P)`, while
the computational cost of direct mixture evaluation changes with mixture
complexity.

## Mixture family

Five nested engineering mixtures are studied.

| Case | Components |
| --- | --- |
| C1 | methane |
| C2 | methane + ethane |
| C3 | methane + ethane + propane |
| C4 | methane + ethane + propane + nitrogen |
| C5 | methane + ethane + propane + nitrogen + carbon dioxide |

The C5 mole fractions are:

- methane: 0.80
- ethane: 0.08
- propane: 0.04
- nitrogen: 0.04
- carbon dioxide: 0.04

For C1–C4, the corresponding prefix is retained and renormalized.

Because species are added as component count increases, this family changes
both component count and mixture identity. It therefore represents an
engineering progression rather than a controlled component-count-only
experiment.

- 1
- 10
- 100
- 1,000
- 10,000
- 100,000

Batch size is an operating condition and MUST NOT be treated as a Pareto
objective.

Results from different batch sizes MUST NOT be placed on a common global
Pareto frontier.

## Direct implementations

The direct EOS evidence contains:

- scalar CPU
- OpenMP CPU with 1, 2, 4, and 8 threads
- generic resident CUDA mixture evaluation
- fixed-composition resident CUDA mixture evaluation

All exact implementations have approximation error zero.

Within a `(mixture, batch)` operating condition, exact implementations may
be compared by runtime. Since their approximation error is identical,
only the fastest exact implementation can be Pareto-optimal.

Small timing differences between the two resident CUDA implementations
must not be overinterpreted.

## Surrogate implementation

Each frozen TDAR approximation is converted to an exact CPWA min/max DAG,
factored bottom-up, optimized using finite-library CP-SAT extraction, and
compiled as a fused CUDA kernel using the min-live schedule.

The approximation itself is not retrained or resampled during this process.

For every surrogate retain:

- validation error
- ns/evaluation
- DAG node counts
- executed operation count
- live slots
- register count
- spill-store bytes
- spill-load bytes
- stack-frame bytes
- CPU/CUDA validation delta

The complete surrogate hardware tensor contains:

5 mixtures × 7 budgets × 7 batch sizes = 245 measurements.

## Timing semantics

Direct and surrogate measurements both characterize warm resident
execution, but use different timing harnesses.

The CPWA CUDA benchmark:

- performs 5 warm-up launches
- synchronizes before timing
- performs 20 measured launches
- uses CUDA events
- synchronizes each stop event
- reports the median
- excludes host/device transfers from the timed interval

The direct ThermoGPU benchmark uses calibrated repeated calls and median
sampling.

Consequently, large differences are engineering-significant, while very
small percentage differences between implementations must not be given
strong interpretation.

## Pareto definition

A separate Pareto problem is constructed for every `(mixture, batch)`
operating condition.

There are therefore:

5 mixtures × 7 batch sizes = 35 Pareto problems.

Each candidate has objectives:

1. minimize validation RMSE
2. minimize execution time in ns/evaluation

Exact methods have:

    RMSE = 0

Surrogates use their measured frozen-validation RMSE.

Candidate A dominates candidate B iff:

    A.rmse <= B.rmse
    A.ns_per_eval <= B.ns_per_eval

and at least one inequality is strict.

No artificial epsilon may be substituted for exact error zero.

## Primary derived questions

The analysis must determine:

1. Which exact implementation is fastest for each `(mixture, batch)`?
2. At what batch size does resident GPU execution become preferable to CPU
   execution for each mixture?
3. Which surrogate budgets lie on each batch-conditioned Pareto frontier?
4. At what approximation error does a surrogate first become faster than
   the best exact implementation?
5. How does this crossover change from C1 through C5?
6. How does surrogate execution cost vary with approximation budget?
7. Where do register pressure and spilling alter the accuracy/performance
   frontier?
8. Does increasing physical-model complexity increase the economic value
   of approximation while surrogate input dimension remains fixed?

## Hardware-resource hypothesis

Increasing approximation budget does not necessarily produce a smooth
increase in execution cost.

Large DAGs can cross GPU resource thresholds, producing:

- high register usage
- register spilling
- stack-frame growth
- discontinuous increases in execution time

These effects are part of the engineering result and must not be smoothed
away.

## Interpretation constraints

The study must state explicitly that:

- composition is fixed during each surrogate evaluation;
- the surrogate predicts Z only;
- the exact EOS implementation computes a richer thermodynamic result;
- binary interaction coefficients are zero;
- C1–C5 changes species identity as well as component count;
- the domain is limited to 250–350 K and 1–10 MPa;
- the study represents one hardware/software environment;
- equal-accuracy conclusions are based on measured budgets, not interpolated
  surrogate sizes;
- timing harnesses differ between direct and surrogate execution;
- tiny timing differences should not be overinterpreted.

A separate synthetic duplicated-component experiment may be used as
supporting evidence for controlled arithmetic scaling, but it must not be
presented as a physical 8- or 16-species mixture.

## Reproducibility

Case Study 2 should follow the evidence/derivation distinction established
by Case Study 1.

A reproduction mode must:

- never rerun TDAR sampling;
- never regenerate frozen upstream physical evidence;
- validate retained raw evidence;
- regenerate processed tables;
- regenerate Pareto classifications;
- regenerate figures;
- regenerate analysis and report artifacts deterministically.

Evidence acquisition and deterministic analysis are separate pipeline
